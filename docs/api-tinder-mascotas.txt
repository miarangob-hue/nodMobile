API requerida para un "Tinder de mascotas"
============================================

Objetivo asumido
----------------
Permitir que los tutores descubran mascotas compatibles, indiquen interés con
un swipe y, cuando el interés sea mutuo, obtengan un match para conversar.
El mismo diseño puede adaptarse a adopción; en ese caso el like no es mutuo y
se convierte en una solicitud enviada al refugio o responsable.

No se necesita una API pública de Tinder. La funcionalidad debe implementarse
en el backend propio de NOD, reutilizando la autenticación, clientes, mascotas
y carga de archivos que ya existen en el proyecto.


APIs propias imprescindibles (MVP)
==================================

1. Perfil social de la mascota
------------------------------

GET /pets/{pet_id}/social-profile

Respuesta:
{
  "pet_id": "uuid",
  "display_name": "Luna",
  "bio": "Juguetona y sociable",
  "species": "dog",
  "breed": "mestiza",
  "sex": "female",
  "birth_date": "2022-05-10",
  "size": "medium",
  "energy_level": "high",
  "temperament_tags": ["sociable", "juguetona"],
  "looking_for": ["playdate", "walk"],
  "vaccinated": true,
  "sterilized": true,
  "photos": [
    { "id": "uuid", "url": "https://...", "position": 1 }
  ],
  "location": {
    "latitude": -33.45,
    "longitude": -70.66,
    "comuna": "Santiago"
  },
  "discovery_enabled": true
}

PUT /pets/{pet_id}/social-profile
Body: los mismos campos editables del perfil.

POST /pets/{pet_id}/social-profile/photos
Body multipart/form-data: file, position.

DELETE /pets/{pet_id}/social-profile/photos/{photo_id}

Reglas:
- Sólo el tutor propietario puede crear o modificar el perfil.
- No exponer dirección exacta, email ni teléfono.
- Redondear coordenadas o devolver sólo distancia/comuna a otros usuarios.
- Validar tipo, peso y tamaño de imágenes; eliminar metadatos EXIF.


2. Preferencias de descubrimiento
---------------------------------

GET /pets/{pet_id}/discovery-preferences

PUT /pets/{pet_id}/discovery-preferences
Body:
{
  "max_distance_km": 15,
  "species": ["dog"],
  "sex": ["male", "female"],
  "min_age_months": 6,
  "max_age_months": 120,
  "sizes": ["small", "medium", "large"],
  "looking_for": ["playdate", "walk"],
  "required_vaccinated": true
}


3. Feed de candidatos
---------------------

GET /discovery/candidates
Query:
- pet_id: uuid requerido
- cursor: string opcional
- limit: número opcional, máximo recomendado 30

Respuesta:
{
  "items": [
    {
      "pet_id": "uuid",
      "display_name": "Max",
      "age_months": 30,
      "species": "dog",
      "breed": "mestizo",
      "sex": "male",
      "size": "medium",
      "bio": "Le encanta correr",
      "photos": ["https://..."],
      "distance_km": 3.4,
      "comuna": "Providencia",
      "temperament_tags": ["activo", "sociable"],
      "looking_for": ["playdate"],
      "compatibility_score": 0.86
    }
  ],
  "next_cursor": "opaque-string|null"
}

El backend debe excluir:
- La misma mascota y las mascotas del mismo tutor.
- Perfiles desactivados, bloqueados o ya descartados.
- Candidatos fuera de los filtros o la distancia máxima.
- Usuarios suspendidos y perfiles reportados que estén en revisión.

Para el MVP, compatibility_score puede ser una fórmula simple basada en
distancia, especie, tamaño, edad, energía, intereses y temperamento. No hace
falta inteligencia artificial.


4. Swipes e intereses
---------------------

POST /discovery/swipes
Body:
{
  "actor_pet_id": "uuid",
  "target_pet_id": "uuid",
  "decision": "like"
}

decision: like | pass | super_like

Respuesta sin match:
{
  "matched": false,
  "match": null
}

Respuesta con interés mutuo:
{
  "matched": true,
  "match": {
    "id": "uuid",
    "pet_ids": ["uuid", "uuid"],
    "created_at": "ISO-8601"
  }
}

Requisitos de implementación:
- La operación debe ser idempotente para evitar swipes duplicados.
- Crear el match en una transacción cuando ya exista un like inverso.
- No revelar si la otra persona dio like hasta que exista match.
- Definir límites de swipes por minuto/día para evitar abuso.


5. Matches
----------

GET /matches?pet_id={uuid}&cursor={cursor}&limit=20

GET /matches/{match_id}

DELETE /matches/{match_id}
Efecto: deshacer match y cerrar el chat para ambos participantes.

Respuesta de listado:
{
  "items": [
    {
      "id": "uuid",
      "pet": { "id": "uuid", "display_name": "Max", "photo_url": "https://..." },
      "last_message": { "text": "Hola", "created_at": "ISO-8601" },
      "unread_count": 1,
      "created_at": "ISO-8601"
    }
  ],
  "next_cursor": "opaque-string|null"
}


6. Chat entre tutores
---------------------

GET /matches/{match_id}/messages?cursor={cursor}&limit=50

POST /matches/{match_id}/messages
Body:
{
  "client_message_id": "uuid",
  "text": "¿Coordinamos un paseo?",
  "attachment_id": null
}

POST /matches/{match_id}/messages/read
Body: { "last_read_message_id": "uuid" }

WebSocket recomendado:
wss://api.ejemplo.cl/realtime?token={access_token}

Eventos:
- message.created
- message.read
- match.created
- match.deleted

Para un primer MVP se puede usar polling cada 5-10 segundos y agregar
WebSocket después. Sólo los tutores incluidos en el match pueden leer o enviar
mensajes.


7. Seguridad: bloquear y reportar
---------------------------------

POST /users/{user_id}/block
DELETE /users/{user_id}/block
GET /users/me/blocks

POST /reports
Body:
{
  "target_type": "user",
  "target_id": "uuid",
  "reason": "harassment",
  "details": "string opcional",
  "evidence_attachment_ids": ["uuid"]
}

reason sugerido:
- fake_profile
- inappropriate_content
- harassment
- animal_welfare
- scam
- other

Bloquear debe ocultar inmediatamente ambos perfiles, eliminar el match y
evitar nuevos mensajes. Los reportes deben quedar disponibles en una cola de
moderación administrativa.


8. Notificaciones push
-----------------------

POST /devices
Body:
{
  "platform": "ios",
  "push_token": "token",
  "device_id": "uuid"
}

DELETE /devices/{device_id}

Notificaciones mínimas:
- Nuevo match.
- Nuevo mensaje.
- Resultado de una denuncia, cuando corresponda.


APIs o servicios externos opcionales
====================================

1. Mapas y geocodificación
- Google Maps Platform o Mapbox.
- Uso: convertir ubicación en comuna/coordenadas y calcular distancia.
- Alternativa económica para el MVP: guardar latitud/longitud del dispositivo
  y calcular distancia en PostgreSQL con PostGIS.

2. Notificaciones
- Expo Push Notifications, apropiado para esta app Expo/React Native.
- Alternativas: Firebase Cloud Messaging y Apple Push Notification Service.

3. Imágenes
- Reutilizar la API de archivos ya existente en NOD.
- Almacenamiento posible: Amazon S3, Cloudflare R2 o Supabase Storage.
- Usar URLs firmadas para subir y un CDN para servir las fotos.

4. Chat en tiempo real
- Backend propio con WebSocket.
- Alternativas administradas: Stream Chat, Sendbird, Firebase o Supabase
  Realtime. Son opcionales; aceleran el desarrollo pero agregan costo.

5. Moderación de fotos/texto
- Moderación propia básica más revisión humana para el MVP.
- Un servicio automático puede añadirse más adelante, pero nunca debe sustituir
  el botón de reporte, el bloqueo ni la revisión de casos críticos.

Orden recomendado de implementación
===================================

Fase 1 - MVP:
1. Perfil social y fotos.
2. Preferencias y feed por ubicación.
3. Like/pass y creación de match.
4. Lista de matches y chat con polling.
5. Bloqueo, reporte y límites antiabuso.
6. Push para matches y mensajes.

Fase 2:
1. WebSocket y presencia en línea.
2. Super likes, deshacer swipe y planes pagados.
3. Recomendaciones más sofisticadas.
4. Verificación de tutores y moderación automática.


Variante para adopción
======================

Si "Tinder de mascotas" significa buscar mascotas para adoptar, reemplazar
swipes/matches mutuos por:

GET /adoption/pets
GET /adoption/pets/{pet_id}
POST /adoption/pets/{pet_id}/applications
GET /adoption/applications/{application_id}
PATCH /adoption/applications/{application_id}/status

Estados sugeridos:
submitted | reviewing | interview | approved | rejected | withdrawn

En adopción, el perfil pertenece a un refugio/rescatista, no se debe abrir un
chat hasta que la organización lo permita y conviene incluir requisitos,
historial veterinario, formulario de postulación y trazabilidad de decisiones.


Respuesta de error estándar
===========================

{
  "error": "machine_readable_code",
  "message": "Mensaje legible",
  "details": {},
  "request_id": "uuid"
}

Códigos HTTP principales:
- 200/201: éxito.
- 400: datos inválidos.
- 401: sesión ausente o vencida.
- 403: el usuario no es propietario/participante.
- 404: recurso inexistente u oculto por privacidad.
- 409: swipe o match duplicado/conflictivo.
- 429: límite de acciones excedido.


Decisión práctica para NOD
==========================

Para la primera versión sólo hacen falta tres integraciones externas:
- El servicio actual de archivos para fotos.
- Expo Push Notifications para avisos.
- PostGIS (recomendado) o un proveedor de mapas para búsquedas por distancia.

El feed, los swipes, los matches, el chat, los bloqueos y los reportes deben
ser APIs propias porque contienen las reglas centrales y los datos sensibles
del producto.
